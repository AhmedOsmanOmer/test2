# المعمارية

## الطبقات
1. **الواجهة** (`src/app`) — مكونات خادمية تقرأ البيانات، ومكونات عميل للتفاعل فقط.
2. **إجراءات الخادم** (`src/server/actions.ts`) — تتحقق من الجلسة، تستدعي الخدمة، تعيد رسالة آمنة (أخطاء التحقق تُعرض كرسالة عربية تذكر الحقل).
3. **الخدمات** (`src/server/services`) — **المكان الوحيد** لقواعد العمل والتحقق من الصلاحيات ونطاق الطلبات. تستخدمها الواجهة والاختبارات معًا.
4. **منطق نقي** (`src/lib/order-flow.ts`, `order-access.ts`, `permissions.ts`) — بدون قاعدة بيانات، مختبر بالوحدة.

إخفاء الأزرار في الواجهة للراحة فقط؛ الحماية الفعلية في الخدمات. شاشة الإنتاج تقرأ بقائمة حقول بيضاء صريحة، فلا تُقرأ أي حقول مالية من القاعدة أصلًا.

## المال (نموذج مبسّط)
- للطلب **قيمة واحدة** `total` يدخلها شخص مخوّل، و`paidAmount` المبلغ المدفوع، و`depositReceived` تأكيد استلام الدفعة المقدمة. **المتبقي = total − paidAmount** ويُحسب ولا يُخزن.
- لا أسعار للبنود، لا ضريبة، لا خصم، لا تكاليف أو أرباح، لا جداول دفعات أو إيصالات أو فواتير أو عروض أسعار أو مخزون (حُذفت بالكامل).
- `setOrderMoney` (صلاحية `orders.edit_value`؛ المبيعات لطلباته فقط): 0 ≤ المدفوع ≤ القيمة، قفل تفاؤلي، سجل تدقيق قبل/بعد، وحدث في السجل الزمني **بلا أرقام**.
- `setDepositReceived` (صلاحية `orders.set_deposit`): عند التأكيد ينتقل الطلب آليًا من «انتظار الدفعة» كانتقال نظامي، **بلا أي تجاوز**.
- `orderMoneyView(actor, order)` تعيد `{total, paidAmount, remaining}` فقط لمن يملك `orders.view_value`، وإلا `null`. كل الصفحات تمر بها، ولا تُمرَّر المبالغ لمكونات العميل لغير المخوّلين.
- لا مبالغ في نص السجل الزمني ولا في الإشعارات (المبالغ في سجل التدقيق فقط، وهو للمدير العام).

## نطاق الطلبات
- `orderScope(actor)`: من يملك `orders.view_all` يرى كل الطلبات، وغيره (موظف المبيعات) يرى `salesRepId = نفسه` فقط.
- `assertOrderAccess(actor, orderId)` في كل خدمة وإجراء يستقبل معرّف طلب؛ خارج النطاق = «الطلب غير موجود» (404 في الصفحات).
- يُطبَّق في: قائمة الطلبات والكانبان، صفحة الطلب، البحث، صفحة العميل، لوحة التحكم، التسليم وسنداته، صفحات التصميم والإنتاج، تنزيل الملفات، وكل إجراءات الطلب.
- العملاء ظاهرون لكل من يملك `customers.view` دون تقييد، لكن طلباتهم تُعرض حسب النطاق.

## مسار الطلب
```
طلب جديد → مراجعة الطلب → [قيمة الطلب > 0] → انتظار موافقة العميل → انتظار الدفعة المطلوبة
 → [تأكيد استلام الدفعة المقدمة] → بانتظار التصميم → تحت التصميم → مراجعة التصميم → انتظار اعتماد العميل
 → تجهيز المواد (يدوي) → جدولة الإنتاج → تحت الإنتاج → التشطيب والتغليف → فحص الجودة
 → جاهز للتسليم → تحت التسليم (جزئي) → تم التسليم → [سداد كامل] → مكتمل ومغلق
استثناءات: معلق، يحتاج تعديل، إعادة إنتاج، ملغى، مرتجع
```
| القاعدة | التطبيق |
|---|---|
| لا تجاوز للمراجعة بلا قيمة | «أدخل قيمة الطلب أولاً» |
| لا تصميم/إنتاج قبل الدفعة المقدمة | `depositReceived` فقط — لا نسبة ولا تجاوز لأي دور |
| لا إنتاج قبل اعتماد التصميم | `designSatisfied` + منع إنشاء أمر تشغيل |
| لا جاهزية قبل الجودة | كل أوامر التشغيل `QC_PASSED` (أو إعادة إنتاجها اجتازت) |
| لا إغلاق قبل السداد | `paidAmount ≥ total` + تسليم كامل + `orders.close` — الرسالة «الطلب غير مسدد بالكامل» بلا أرقام |
| الإرجاع لمرحلة سابقة | سبب إلزامي، ويشمل الخروج من الحالات الاستثنائية (يُقارن بآخر حالة رئيسية من سجل الحالات) |
| «متأخر» | مؤشر محسوب وليس حالة |

الانتقالات الآلية (تأكيد الدفعة ← تصميم، اعتماد ← تجهيز، إنتاج ← جودة…) تمر بنفس `transitionTx` وقواعدها.

## الإشعارات
- `notify()` (`src/server/services/audit.ts`): يجمع أعضاء الأدوار والمستخدمين المحددين، **يستثني منفّذ الإجراء** والمستخدمين المعطّلين، ويصل كل مستخدم مرة واحدة. الإشعار المرتبط بطلب (`Notification.orderId`) لا يصل لموظف مبيعات إلا إن كان مندوب هذا الطلب.
- داخل المعاملة الواحدة: إن وصل المستخدمَ إشعارٌ أخص عن نفس الطلب (مثل «تم تأكيد الدفعة») فلا يصله إشعار تغيير الحالة العام.
- قواعد المستلمين نقية ومختبرة في `src/lib/notification-rules.ts`:

| الحدث | المستلمون |
|---|---|
| ORDER_NEW | المدير العام، مدير العمليات، مشرف المبيعات، والمندوب إن أنشأ الطلبَ غيرُه |
| ORDER_STATUS_CHANGED (كل انتقال يدوي أو آلي) | المندوب، مدير العمليات، مشرف المبيعات — وللحالات: معلق، ملغى، يحتاج تعديل، مرتجع، إعادة إنتاج: مهم + المدير العام + المكلّفون |
| DEPOSIT_RECEIVED | المندوب، مدير العمليات |
| ORDER_REP_CHANGED | المندوب السابق، الجديد، مدير العمليات |
| ORDER_DUE_CHANGED | المندوب، المكلّفون، مدير العمليات، مشرف المبيعات |
| ORDER_COMMENT | المندوب والمكلّفون عدا كاتب التعليق (نص التعليق لا يُنسخ للإشعار) |
| DUE_SOON / ORDER_LATE | المندوب، مدير العمليات، مشرف المبيعات، المكلّفون (+ المدير العام للتأخر) |

«المكلّفون» = مصممو مهام التصميم المفتوحة وموظفو أوامر التشغيل المفتوحة ومراحلها. لا مبالغ في أي نص إشعار أو حدث.
- التوصيل داخلي بلا خدمات خارجية: `GET /api/notifications/poll?after=` (إشعارات المستخدم نفسه فقط) يستطلعه الجرس في الترويسة كل 15 ثانية (60 في الخلفية، وفورًا عند التركيز وبعد أي إجراء). `GET /notifications/[id]/open` يعلّم إشعار المستخدم نفسه فقط ويحوّل لمسار داخلي فقط.

## استيراد بنود الطلب من Excel
- `exceljs` على الخادم فقط (`serverComponentsExternalPackages`)، ولا يُستخدم `xlsx`. المحلل `src/server/import/order-items-xlsx.ts` والقالب `items-template.ts`، والأعمدة المشتركة في `src/lib/order-item-import.ts` تطابق مخطط البند `src/lib/order-item.ts` (المصدر الوحيد لحقول البند ورسائلها، بلا أي حقل مالي).
- الرفع عبر Route Handler `POST /api/orders/items-import` (جلسة، نفس الأصل، 10 مرات في الدقيقة لكل مستخدم، 5 ميجابايت). فحوصات قبل الفتح: الامتداد، توقيع ZIP، حجم المحتوى بعد فك الضغط من الدليل المركزي (حماية من قنابل ZIP). بعد الفتح: الورقة الأولى، 500 صف، رفض الأعمدة المالية والمجهولة والمكررة، نتائج الصيغ المخزنة فقط، تحويل الأرقام العربية، حد لطول الخلية، ومهلة زمنية.
- معاينة ثم تأكيد: المعاينة تحفظ `OrderItemImport` (البصمة والاسم والحجم والبنود المتحقق منها — لا الملف). التأكيد إجراء خادم بمعرّف المعاينة فقط، يقرأ البنود من القاعدة ويعيد فحص الصلاحية والنطاق والحالة، وينقل الحالة PREVIEW → COMMITTED شرطيًا داخل معاملة واحدة مع إدراج البنود وسجل التدقيق `IMPORT_ORDER_ITEMS` وحدث «تم استيراد N بنداً من ملف Excel» وإشعار المندوب إن استورد غيره. التأكيد المكرر أو المتزامن لا يكرر البنود.
- صلاحية `orders.import_items`: المدير العام، مشرف المبيعات، موظف المبيعات (لطلباته عبر `assertOrderAccess`).

## إثبات التسليم بالصور
- كل تسليم (سجل `Delivery`، جزئي أو نهائي) يتطلب 1-5 صور، مفروضة في الخدمة `createDelivery` نفسها (لا طريق للتسليم بدونها). الصور ملفات `Attachment` من نوع `DELIVERY_PROOF` مرتبطة بالطلب وبسجل التسليم (`deliveryId`)، مخزنة خارج public باسم عشوائي.
- `POST /api/orders/[id]/deliveries` (multipart: بيانات التسليم + الصور، جلسة، نفس الأصل، 20 مرة في الدقيقة). التحقق بالمحتوى (Magic bytes) لا بالامتداد: JPEG وPNG وWebP، ويُرفض HEIC برسالة عربية، 8 ميجابايت للصورة. تُكتب الملفات أولًا ثم تُسجَّل مع التسليم في معاملة واحدة، وتُحذف عند أي فشل؛ والإرسال المكرر (idempotencyKey) لا يكرر التسليم.
- المتصفح يصغّر الصورة إلى 1600 بكسل JPEG قبل الرفع (canvas، بلا مكتبات، يحترم الاتجاه ويُسقط EXIF). الوقت والمستخدم من الخادم فقط.
- العرض عبر مسار الملفات المحمي نفسه (`/api/files/[id]`) بنطاق الطلب: 404 لموظف مبيعات لا يملك الطلب. حدث «تم تسليم الطلب مع N صورة إثبات» وسجل تدقيق `DELIVERY_PROOF_CREATE` (المعرّفات والعدد والبصمات). الحذف للمدير العام فقط بسبب إلزامي (`DELIVERY_PROOF_DELETE`).
- التسليمات السابقة لهذه الميزة بلا صور وتبقى كما هي.

## سلامة البيانات
- **منع التكرار:** `idempotencyKey` لتسجيل الإنتاج والتسليم.
- **التزامن:** قفل تفاؤلي (`Order.version`) لتغيير الحالة والمبالغ وتأكيد الدفعة.
- **المعاملات:** كل عملية متعددة الخطوات داخل `$transaction`.
- **إلحاقي:** السجل الزمني وسجل التدقيق لا يُعدَّلان ولا يُحذفان من التطبيق.
- **الترحيل:** `prisma/migrations` (أول ترحيل `init`)؛ الإنتاج بـ `prisma migrate deploy`.

## الأمان
- كلمات المرور bcrypt (cost 12)؛ الجلسة رمز عشوائي 256-bit في كوكي HttpOnly/Secure/SameSite، ويُخزن في القاعدة بصمته SHA-256 فقط.
- قفل الحساب 15 دقيقة بعد 5 محاولات، وحد 30 محاولة فاشلة لكل IP خلال 15 دقيقة.
- إجبار تغيير كلمة المرور المؤقتة؛ لا كلمة مرور افتراضية ثابتة (المشغّل يولد كلمة عشوائية أول مرة).
- CSRF: Next.js يتحقق من Origin. XSS: React + CSP صارمة؛ `unsafe-eval` مسموح في وضع التطوير فقط.
- الملفات خارج `public` بأسماء عشوائية، والتنزيل يتحقق من الصلاحية ونطاق الطلب. حد الرفع موحّد في `src/lib/upload-limit.json`.
- `next` 14.2.35 (يعالج CVE-2025-29927).
